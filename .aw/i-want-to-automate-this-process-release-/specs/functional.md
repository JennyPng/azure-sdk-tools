# Functional Specification — Azure SDK Release Management

This document describes the current behavior of Azure SDK release management automation, focusing on user-visible workflows and edge cases.

## Current Release Management Workflows

### 1. Monthly Release Cycle (Current Model)

**Overview**: Azure SDK historically followed a monthly release cadence where:
- Release notes are collected for packages released during a calendar month
- Release kickoff email is sent at start of month
- Code complete date triggers final editorial pass
- Release blog ships at end of month

**Current State** (per task description):
- Monthly model has "unnecessary overhead"
- Simpler model emerging: teams release anytime, included in month's release notes
- Discussion of moving away from monthly releases entirely
- If monthly model abandoned: service must ship all languages at same time (feature alignment)

### 2. Release Notes Generation & Review

#### Automated PR Creation

**Trigger**: External pipeline (`azure-sdk-version-updater`) runs regularly (frequency not specified in codebase)

**Behavior**:
1. Queries package feeds (NuGet, PyPI, npm, Maven) for newly published packages
2. Extracts changelog entries from published packages
3. Generates/updates `_data/releases/YYYY-MM/{language}.yml` in `Azure/azure-sdk` repo
4. Creates PR with title: `"{language} release notes for the YYYY-MM release"`
5. Continuously updates PR as new packages are published

**Example PR**: Azure/azure-sdk#9846 (dotnet release notes for 2026-05)

**Current Issue** (per task description):
- "true review isn't usually necessary"
- "desire to automate this more"
- Generic release note PRs are OK to auto-merge
- Language-specific PRs need language team approval
- Some PRs have had broken CI (bad links for new release tags)

#### Review Workflow

**Engineering Lead Responsibilities**:
- Verify package was picked up by automation (24hr lag expected)
- Review generated entry in `_data/releases/YYYY-MM/{language}.yml`
- Suggest corrections via GitHub suggestions
- Add missing packages if automation hasn't run since release

**Release Manager Responsibilities**:
- Hide entries for packages not in release (set `Hidden: true`)
- Final editorial pass after code complete
- Merge PR
- Link release notes into table of contents

**Content Requirements**:
- List of packages with installation instructions
- Developer impacting changes per package:
  - `Features Added` — New features
  - `Breaking Changes` — Compatibility breaks, deprecations, removals
  - `Bugs Fixed` — Important bug fixes (not every minor fix)
- Boilerplate text with latest release links
- Point-in-time download/source/docs table

**Edge Cases**:
- Package released after official release date → Add to current month's release notes
- Package with no dev-impacting changes → Can omit or add note "This release contains bug fixes to improve quality"
- Out-of-band release → Submit PR to current month, tag language release owner

### 4. Release Plan Tracking

#### Creation

**Trigger**: Developer or PM initiates release planning

**Methods**:
1. **Via CLI**: `azsdk release-plan create --typespec-path <path> --release-month "Month YYYY" --api-release-type "GA" --sdk-release-type "stable"`
2. **Via MCP/Copilot**: `azure-sdk-mcp:azsdk_create_release_plan`
3. **Via Script**: `./eng/common/scripts/Prepare-Release.ps1 <PackageName>`

**Work Item Fields Set**:
- `Custom.SDKReleasemonth` — Target release month (e.g., "June 2026")
- `Custom.ApiSpecProjectPath` — TypeSpec project path
- `Custom.SDKtypetobereleased` — "beta" or "stable"
- `Custom.ReleasePlanType` — "Private Preview", "Public Preview", or "GA"
- `Custom.ProductName`, `Custom.ServiceName` — Product/service identifiers
- `Custom.SDKLanguages` — Languages to be released
- Per-language package names (`Custom.{Lang}PackageName`)

**Validation**:
- TypeSpec path must be relative to repo root
- API release type must match spec PR repository type
- SDK release type is separate from API release type (explicitly asked)

**Edge Case**: If release plan exists for same TypeSpec path but different API release type, force-creates new plan (`forceCreateReleasePlan: true`)

#### Update

**Trigger**: SDK PR created, spec PR updated, package details change

**Methods**:
1. **Link SDK PR**: `azsdk_link_sdk_pull_request_to_release_plan`
   - Updates `Custom.SDKPullRequestFor{Lang}`
   - Extracts PR status, checks, approvals from GitHub
2. **Update API Spec PR**: `azsdk_update_api_spec_pull_request_in_release_plan`
   - Updates child "API Spec" work item's `Custom.ActiveSpecPullRequestUrl`
3. **Update SDK Details**: `azsdk_update_sdk_details_in_release_plan`
   - Runs TypeSpec emitter to extract package names
   - Updates `Custom.{Lang}PackageName` fields
4. **Update Metadata**: `azsdk_update_release_plan`
   - Updates spec PR, TypeSpec path, SDK release type, service/product IDs

**Dashboard Sync**:
- Dashboard caches release plans (1hr TTL)
- Auto-refreshes server-side via `setInterval`
- Client polls `/api/release-plans` every hour
- PR details fetched on-demand with 15min cache

#### Completion

**Trigger**: Package published to feed (NuGet, PyPI, npm, Maven)

**Pipeline Step** (`mark-release-completion.yml`):
1. SDK release pipeline publishes package
2. Pipeline writes package info JSON (name, version)
3. Calls `Mark-ReleasePlanCompletion.ps1`
4. Script invokes `azsdk release-plan update-release-status`

**Tool Behavior** (`PackageReleaseStatusTool.cs`):
1. Searches for "In Progress" release plans matching package name + language
2. If multiple found: prefers plan with "Merged" PR status
3. Updates work item fields:
   - `Custom.ReleaseStatusFor{Lang}` → "Released"
   - `Custom.ReleasedVersionFor{Lang}` → version number
4. Checks if all required languages are complete:
   - Management: .NET, Java, JavaScript, Python, Go
   - Data plane: .NET, Java, JavaScript, Python
5. If complete (all "Released" or "Approved" exclusion):
   - Sets `System.State` → "Finished"

**Edge Cases**:
- No release plan exists → Script logs warning, continues (not all releases have plans)
- Multiple active plans → Selects first with "Merged" PR, else first in list
- Partial releases → Plan stays "In Progress" until all languages complete
- Excluded language (with "Approved" justification) → Counts as complete

### 5. Package Version & Changelog Management

#### Version Update

**Tool**: `Prepare-Release.ps1`

**Behavior**:
1. Reads current version from package project file
2. Prompts user for new version (default: current version)
3. Validates SemVer format
4. Calculates release date:
   - Default: first Tuesday after first Friday of month
   - If past month's release date and before 15th: today
   - If past 15th: next month's release date
   - Manual override via `-ReleaseDate` parameter
5. Creates/updates DevOps "Package" work item (separate from Release Plan)
6. Checks APIView status (requires Key Vault access)
7. If not `-ReleaseTrackingOnly`:
   - Calls language-specific `SetPackageVersion` function
   - Updates project version files
   - Updates changelog entry title
8. Validates changelog has proper entry for version

**Edge Case**: Latest changelog entry already has release date → Prompts whether to replace

#### Changelog Update

**Tool**: `Update-ChangeLog.ps1`

**Behavior**:
1. Parses existing CHANGELOG.md entries
2. If version exists:
   - If release status matches → No change
   - If `Unreleased` → Skip (already marked unreleased)
   - If new date is older → Skip with warning
3. If `-ReplaceLatestEntryTitle`:
   - Removes latest entry
   - Inserts new entry with same content, new version/date
4. If version doesn't exist:
   - Creates new entry at top with boilerplate sections
5. Writes updated changelog

**Entry Format**:
```markdown
## {Version} ({YYYY-MM-DD}) / (Unreleased)

### Features Added
### Breaking Changes
### Bugs Fixed
### Other Changes
```

**Edge Cases**:
- Adding older version than latest → Warning logged, proceeds
- Version exists with release date + trying to mark Unreleased → Skip
- No package properties found → Error exit

### 6. Dashboard Action Determination

**Per-Language Action Buttons** (`public/app.js`):

**"Generate SDK"**:
- Condition: No SDK PR URL
- User action: Trigger SDK generation pipeline

**"Link PR"**:
- Condition: SDK PR exists but is closed (not merged)
- User action: Find correct PR, link via `azsdk_link_sdk_pull_request_to_release_plan`

**"Fix Checks"**:
- Condition: PR has failing checks
- User action: Debug CI failures, push fixes

**"Merge PR"**:
- Condition: PR approved + all checks passing + not merged
- User action: Merge SDK PR

**"Release"**:
- Condition: PR merged + release status ≠ "Released"
- User action: Trigger release pipeline

**No Action**:
- Condition: Released OR excluded
- Display: Released version OR "Excluded: {reason}"

**Package Feed Links**:
- Only shown when `ReleaseStatusFor{Lang}` === "Released" (exact match)
- Links to NuGet, PyPI, npm, Maven Central, GitHub (Go) with icons

### 7. Namespace Approval Linking

**Trigger**: First management plane release for new service

**Tool**: `azsdk_link_namespace_approval_issue`

**Behavior**:
- Links GitHub issue to release plan
- Updates `Custom.NamespaceApprovalIssue` field
- Required for ARM resource providers

## Edge Cases & Current Limitations

### Timing Issues
- **24hr lag**: Packages may not appear in automation immediately after release
- **Monthly cutoff**: Packages released after official date must be added to current month
- **Cache staleness**: Dashboard shows stale data for up to 1 hour

### Data Consistency
- **Multiple active plans**: Tool picks first with "Merged" PR, may not be correct
- **Orphaned plans**: Old plans stay "In Progress" if languages never release
- **Exclusion tracking**: Requires manual "Approved" status in `ReleaseExclusionStatusFor{Lang}`

### Review Process
- **Broken CI links**: PRs have had issues with bad release tag links
- **Manual intervention**: Generic PRs could auto-merge but currently don't
- **Language approval**: Language teams must approve language-specific PRs (manual gate)

### Automation Gaps
- **Latest release data CSV**: Generation/merge process not automated in this repo
- **Release structure generation**: Monthly sidebar nav hardcoded (pipeline not in this repo)
- **Release blog**: Mentioned in docs but tooling not in this repo
- **Kickoff email**: Manual process (template exists)

## Current Behavior: Auto-Merge Eligibility (Hypothetical)

**Safe to Auto-Merge**:
- Generic release note updates (all languages)
- Updates to existing entries with no structural changes
- Addition of new packages with complete changelog content

**Requires Human Review**:
- Language-specific PRs (per language team policy)
- Breaking changes in any package
- First release of new service/package
- Structural changes to release note format
- Missing or incomplete changelog content

**Cannot Auto-Merge** (current state):
- All PRs currently require manual merge by release manager
